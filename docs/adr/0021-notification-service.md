# ADR-0021: Central Notification service; OTP via synchronous internal call; SMTP relay adapter
Date: 2026-11-12 · Status: Accepted (guide ADR-019)
## Context
Phase 1 only *logged* OTPs, and every service that wanted to email someone would have needed its own retry story, templates and unsubscribe handling. Channel policy (System Scenarios §7): email for transactional mail, SMS only for OTP/security (it costs money), push for order status/promos, in-app for everything.
## Decision
One service (`src/services/notifications`, port 5107, `notifications_db`) owns every outbound message. Events (`UserRegistered`, `OrderPaid`, `OrderStatusChanged`, `OrderCancelled`, `PaymentFailed`, `SellerApproved/Rejected`, `InventoryLowStock`) become queued messages + in-app inbox items, deduplicated by message id, filtered by per-user preferences (`security` can't be switched off; promos are opt-in). A `DeliveryWorker` claims batches with `FOR UPDATE SKIP LOCKED` and a 2-minute lease, sends outside the transaction, backs off 1m→5m→30m→2h→12h and dead-letters after 5 attempts (admin list + requeue). **OTPs are a synchronous internal REST call** from Identity (`POST /api/v1/internal/notifications/otp`) — never an event, never stored. Email goes over plain **SMTP via MailKit** (Mailpit locally; SendGrid/SES SMTP relays in production); SMS and push sit behind adapter interfaces chosen by config. Contacts are a local read-model built from `UserRegistered`.
## Alternatives
- Each service sends its own email (six retry stories) · OTP as an event (the secret would sit in RabbitMQ, outbox tables and logs) · vendor SDKs (lock-in) · sending inline from consumers (slow SMTP blocks the queue; retries re-send).
## Consequences
+ One queue, one retry policy, one place to add a channel; OTP delivery failure is non-fatal (registration still answers 202, the resend cooldown is lifted). Competing workers are safe without a coordinator (tested with two workers × 100 messages). − Templates are English only until the Localization service (Phase 3). − Staff notifications (KYC queue, dead-letter alerts) need role-based recipients → Phase 3 admin panel. − `OrderCancelled` with a `PAYMENT_FAILED` reason is not announced separately (the `PaymentFailed` message already tells the customer). − In staging the SMS adapter is still the logging one, so staging logs can contain OTPs (DevTools environment only).
